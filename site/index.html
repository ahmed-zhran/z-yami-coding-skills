Branch lineage

Every issue already knows where it lands

The base is written on the issue before any branch is cut. The checkout you happen to have open is never the destination.

  1. 01
    Release release/<N>

    Cut from main. Holds every feature of the cycle. The version tag lands on the merge into main.

  2. 02
    Spec spec/<issue>

    One feature, one branch. Lands into the open release. Git cannot nest branch names, so the level lives in the name and the parent lives in the base.

  3. 03
    Ticket ticket/<issue>-<slug>

    A tracer path through the stack. Lands into its spec. A bug lands into the open release, a hotfix from the production tag, or main.

Ship doors

The door you type owns the land gate

Higher doors land everything beneath them. You only approve the level you invoked.

Ticket door

You approve the ticket merge

One issue, one worktree, one pull request into the recorded base. Review runs before the PR opens. Landing waits on you, unless the branch policy says review: auto and CI is green.

You · ticket PR → base

Spec door

The session lands every ticket

Ready tickets run in their own Herdr sessions. The parent steers them, waits for green CI, and merges each ticket into spec/<issue>. You approve only the spec pull request into the release.

Session · tickets · You · spec PR → release

Release door

The session lands tickets and specs

Features ship one after another. Each spec's tickets and the spec itself merge under release authority. Tests, code review, and security review run before the release pull request. You approve only that PR into main. Then the tag.

Session · tickets + specs · You · release PR → main

The gate

The next release waits on open boxes

docs/agents/pending-release.md lands on main with every box open: retro, reflect, learnings, debt, ADRs, architecture, risk, open decisions, and a skills update. The agent does not check those boxes. A hotfix from a production tag skips this gate.

Why a base

With a recorded base, and without one

If the base line is missing, the work stops. Guessing from the open checkout is how releases get tangled.

No recorded base

The open checkout decides

  • The agent builds on whatever branch is checked out.
  • A ticket can merge into main, a release, or a branch that happened to be open.
  • Two features share one branch and one pull request.
  • A fix for a shipped bug can land on an unreleased branch and never reach production.

Yami Coding

The issue decides

  • The base is written when the issue is created.
  • A ticket lands into spec/<issue>. That spec lands into release/<N>. The release lands on main.
  • One release holds every feature. Each feature keeps its own spec branch.
  • A bug lands into the open release, a hotfix from the production tag, or main.

Release cycle

Open, fill, review, tag, hold

Spec and ticket branches die when they land. The release branch lives until the tag. Changelog entries compile at finish.

  1. 01Open/release start cuts release/<N>. An open gate box stops this.
  2. 02Fill/ship-release ships each feature through its tickets and lands the specs.
  3. 03ReviewFull tests, code review, and security review on the release diff against main.
  4. 04TagYou approve the release PR. The tag is the merge commit on main.
  5. 05HoldThe gate file stays open on main. A shipped bug uses /release hotfix.

Get it

Install one route

The plugin and skills.sh both install this package. Using both leaves every skill twice. Pick one.

claude plugin marketplace add ahmed-zhran/z-yami-coding-skills
claude plugin install z-yami-coding-skills@z-yami
codex plugin marketplace add ahmed-zhran/z-yami-coding-skills
codex plugin add z-yami-coding-skills@z-yami
npx skills@latest add ahmed-zhran/z-yami-coding-skills -a <agent>

Run /setup-z-yami-coding-skills once in the project. When you are unsure which skill fits, run /ask-yami.
