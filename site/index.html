What this package adds

A skill is a procedure the agent follows. These are the ones that change how code actually ships.

Branch lineage

Every issue records the branch it lands into when it is created. A spec ticket lands in spec/<issue>. That spec lands in release/<N>. The release lands on main.

More than one spec

/ship-release asks what the release actually ships. Two features become two specs. It runs /ship-spec once per feature and waits until that spec has landed before the next.

One session per ticket

Inside Herdr, each ready ticket gets its own session. On the TUI that is a pane. On Desktop it is a terminal in the current tab. The session stops when the pull request is open. You approve it. Blocked tickets wait.

Review before the tag

The release diff gets a standards review and an exploit-focused security review. You test it yourself. The tag happens after that approval, not when the agent feels done.

A gate after the tag

Retro, learnings, debt, architecture, risk, and a skills update sit in docs/agents/pending-release.md. The next release refuses to start while a box is open.

Updates that rewrite policy

/sync-skills replaces this package's skills, then applies migration records to files like docs/agents/branching.md. Your review mode and default base stay.

Where a change lands

The base is a line on the issue, written before any branch is cut. The checkout you happen to have open is not a base.

01
Release

release/<N> is cut from main. It is the branch that eventually gets the version tag. A release can contain several specs.

02
Spec

One feature, one spec issue, one branch named spec/<issue>. Git cannot hold both release/1 and release/1/spec/1, so the name shows the level and the base shows the parent.

03
Ticket

A ticket cut from a spec lands back into that spec. A bug lands into the open release, into a hotfix cut from the production tag, or into main when nothing is open.

04
You

Four approvals: the ticket list, each ticket's pull request into the spec, that spec's pull request into the release, and the release itself. /land merges into the recorded base and restacks whatever was stacked on it.

With a base, and without one

A base is the branch an issue lands into, written on the issue before any branch is cut. If that line is missing, the work stops.

No recorded base

The open checkout decides

  • The agent builds on whatever branch is checked out.
  • A ticket can merge into main, a release, or a branch that happened to be open.
  • Two features share one branch and one pull request.
  • A fix for a shipped bug can land on an unreleased branch and never reach production.

Yami Coding

The issue decides

  • The base is written when the issue is created.
  • A spec ticket lands into spec/<issue>. That spec lands into release/<N>. The release lands on main.
  • One release holds every spec it needs. Each spec keeps its own branch.
  • A bug lands into the open release, a hotfix cut from the production tag, or main when nothing is open.

You hold every stop

From the release down to a single ticket, the agent waits. You can run the whole release with /ship-release, or drive one level yourself.

Before branches

You approve the breakdown

Each feature becomes one spec, and you approve that spec's tickets before they are published. A release with two features approves two lists, one spec at a time.

Ticket level

The pane stops at the pull request

Spec level

The spec lands into the release

Release level

Tests, security, then your testing

The release diff is reviewed for standards and for exploits. You test it. The pull request into main uses a merge commit. The tag is the merge commit on main, after you approve.

After the tag

The next release waits on you

docs/agents/pending-release.md lands on main with every box open: retro, reflect, learnings, debt, ADRs, architecture, risk, open decisions, and a skills update. Checking a box is a later commit. The agent does not check them.

The release cycle

A release branch is long-lived until the tag. Spec branches and ticket branches are deleted when they land. The changelog is compiled at the tag, from entries written as the work landed.

  1. 01Open/release start cuts release/<N> from main. An open gate box stops this.
  2. 02FillSpecs and tickets land into it. An unreleased bug found here is a ticket whose base is the release, with no changelog entry.
  3. 03NotesEach change users will notice already has a changelog entry. Finish compiles them into a version and a CHANGELOG.md section.
  4. 04TagYou approve the release pull request. The tag goes on the merge commit on main. The release branch is then deleted.
  5. 05HoldThe gate file is on main with open boxes. The next release waits. A shipped bug uses /release hotfix <tag> instead.

Documentation the agent maintains

The glossary and ADRs come from the forked grilling flow. These are the files this package adds around them.

Policy, once

/setup-z-yami-coding-skills writes docs/agents/: the issue tracker, labels, branching.md, and, in a monorepo, the surface map.

While you shape

/grill-with-docs and domain modeling keep GLOSSARY.md and ADRs current. /stack-decision and /surface-architecture record the stack and the code architecture for a surface.

While you build

A user-visible change gets a changelog entry. A non-obvious fix gets a solution note in docs/solutions/. Mermaid diagrams are validated before they are committed.

After a session

/reflect turns lessons into edits of skills and docs. /retro is one of the boxes that blocks the next release.

When this package changes a file you keep

/sync-skills shows the changelog, then applies a migration record. Your review mode, default base, and stacking choices stay. A dirty copy of a skill from this package stops the update.

Prose people read

unslop strips AI tells from pull requests, changelogs, and docs. writing-for-agents, kept from the fork, is how docs for the agent are written.

What was brought in, and what was rewritten

Some skills are vendored from other authors and adapted. Some forked skills were rewritten so they obey the base line. Licenses stay with the folders.

Brought in

  • Herdr, herdr-core, and herdr-app, Apache-2.0. /ship-spec opens one session per ready ticket on the TUI or on Desktop. The guide only helps a human install it.
  • security-review, adapted from Fabricio Telles, Apache-2.0. Findings need an attacker, an action, and a result.
  • skill-eval, adapted from Fabricio Telles, Apache-2.0. Scores a skill and its trigger.
  • caveman, Julius Brussee, Apache-2.0. Terse chat. Files stay full prose.
  • unslop, from Conor Bronsdon's avoid-ai-writing, MIT.
  • mermaid-validator, dt418, MIT.
  • deep-review follows the thermo-nuclear review in cursor/plugins. implement absorbed ponytail's smallest-complete-change ladder. Ponytail is not its own skill.

Rewritten from the fork

  • ask-yami routes the lineage, release, surface, review, and learning flows.
  • setup also writes branching and surfaces.
  • to-spec and to-tickets record the base, then cut the branch from it.
  • implement opens a pull request into that base and writes a changelog entry.
  • code-review uses the recorded base as the fixed point and can add Security and Deep.
  • triage and diagnosing-bugs set a bug's base from where it shipped: the open release, a hotfix cut from the production tag, or main.

Install one route

The plugin and skills.sh both install this package. Using both leaves every skill twice. Pick one.

claude plugin marketplace add ahmed-zhran/z-yami-coding-skills
claude plugin install z-yami-coding-skills@z-yami
codex plugin marketplace add ahmed-zhran/z-yami-coding-skills
codex plugin add z-yami-coding-skills@z-yami
npx skills@latest add ahmed-zhran/z-yami-coding-skills -a <agent>

Run /setup-z-yami-coding-skills once in the project. When you are unsure which skill fits, run /ask-yami. When skills.sh asks which skills to take, include setup-z-yami-coding-skills.
