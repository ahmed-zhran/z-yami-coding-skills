Release cycle

Ship the cycle. Changelog every ticket.

Each ticket writes its own changeset before it lands. The release compiles those notes into CHANGELOG.md and the version bump. No orphan merges without a human-readable why.

01 Ticket lands Changeset file in .changeset/ names the skill and the user-visible why.
02 Spec lands Feature merges into release/N. Ticket notes stay stacked for the bump.
03 Release PR Version workflow opens chore: version skills from the stacked changesets.
04 Tag on main You land the release. CHANGELOG section + tag sit on the merge commit.

.changeset/ · per ticket

ticket/42-cli ask-yami-what-next.md Router now points “what next” at ship doors
ticket/42-docs sync-skills-remote-only.md Install block drops local clone path
ticket/55-steer design-taste-frontend.md Vendored taste kit for landing motion

CHANGELOG.md · at release

## 1.5.0 ask-yami Maps “what next” to the right ship door

→ .changeset/<slug>.md written before the land gate
$ /ship-release · after features land
→ version PR compiles every ticket note into the release section

The orchestrator never leaves the parent tab.

You stay where you typed the ship command. The parent clears allowlist dialogs, packs child panes into a 2×3 grid, and closes them after land.

Screen loop

Allowlist dialogs

Cursor often leaves status as working while a dialog waits. The parent polls the screen and clears each with a run-once y.
